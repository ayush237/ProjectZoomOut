### Task: LEDGER-1 — one spender per run
**Suggested model:** Sonnet — one small design with a named mechanism to verify, a stated behaviour list, and strong existing patterns to copy (the structural pin, the kill-9 child). The risk is a lock that is real in the tests and absent in a command, or one a crash leaves held — so each is shown red, and the live proof is a refusal against the real ledger, not a mock.
**Context:**
- **The ledger is what enforces the spending ceiling, and nothing enforces the ledger.** A run's `cost` lives in its LangGraph checkpoint, in the pipeline's own Postgres. A spending command loads the whole object when it opens the run, adds its own spend in memory and **writes the whole object back** — `RunLedger.record`, `_Narration.checkpoint`, the direct `{"cost": state.cost}` writes in `generate-assets` and `rewrite-leaf`, and the graph's own nodes under `run` and `resume`. Two processes on one run overwrite each other's entries (last writer wins), and each `NarrationBudget` starts from its own copy of `spent_usd`, so **two can each believe they have all the headroom.** The only guard is one sentence in the README: "Run one `narrate` at a time per run."
- **It has held by convention, unverified.** VO-4 and VO-4.1 ran eight real `narrate` invocations by hand, one at a time; VO-4.1's own "no other `narrate` is running" check counted the shell's wrapper processes and was not a gate. Nothing raced — the ledger proved it afterwards. The default is now three attempts a clip, so a second process can over-spend by more than it could when this was first written.
- **Ruled twice that it is a design, not a procedure:** out of ONBOARD-2.1 on 2026-09-25, and **the founder said go on 2026-10-03.** Book #3 is deferred — enhancement work is coming that will reuse `narrate` — so this is no longer a precondition of a second book; it is the guard that makes the next paid run safe.
- **Where the lock can live.** `runs/` is per worktree and gitignored, but **the ledger is in the one shared pipeline Postgres** — so a lock file under `runs/<run>/` would not stop `narrate --run-id ikigai` started from `ZO` while another runs from `ZO-pipeline`. The lock has to live where the ledger does. **Hypothesis: a session-level Postgres advisory lock on a dedicated connection, keyed by the run id** — the server releases it when the connection ends, **including when the process is killed.** Verify it against the code and say where it disagrees (a pooler between the process and Postgres would defeat a session lock; there is none today — `psycopg.connect` goes straight to `:5433`).
- **Facts checked 2026-10-03, by reading each command's body:** `open_run_for_narration` calls `open_run_for_models` first. `open_run_for_models` is called directly by `resume`, `measure-breakdown`, `generate-assets`, `review-track`, `rewrite-leaf` and `balance-distractors`; `generate-covers` (it spends, and writes `cost` through `RunLedger`), `narrate` and `audition-voices` reach it through `open_run_for_narration` — the last two via `_Narration`. **`run` calls `require_paid_tier` itself and never the helper.** `write-drafts` reads the checkpoint with `read_run_state` and writes it back without touching `cost`; `narration-stale`, `status`, `cost` and `purge-raw-text` use `read_run_state` only; `doctor`, `init-db`, `attach-scenario-images`, `check-variety`, `contact-sheet` and `generate-greetings` open no run (the greetings keep their own ledger, `runs/greetings/spend.json`). **L5 is where every command gets classified — trust your own read of the bodies over this list.** `apps/pipeline` is unchanged on `origin/main` since the merge of PR #65 (`aee8c8a`).

**Requirements:** *The behaviours are the requirement; the shapes are hypotheses to verify against the code.*

*Part 1 — the lock.*
- **L1. One spender per run, refused immediately.** A command that would open a run for models while another process holds it **exits at once** — red, bold, exit code 2 like the paid-tier refusal — **before** any client is built, any model, speech or CMS call, and any write to the checkpoint. It names the run, says another process holds it, says **who** if that is cheap to find (hypothesis: set `application_name` on the lock connection to something like `zoomout-pipeline narrate ikigai pid 41233` and read it back from `pg_locks` joined to `pg_stat_activity`: the backend pid and since when), and gives the two ways out — wait for it, or stop it. **No `--force`, no `--wait`.**
- **L2. Taken before the checkpoint is read.** Otherwise a process reads `cost`, waits, acquires after the holder has written, and then overwrites the holder's spend with its own stale copy. In `open_run_for_models` the lock comes **before** `read_run_state`. A test pins the order.
- **L3. Held until the process exits; released on every exit.** The command goes on to spend after the helper returns, so the lock outlives the helper. Normal return, `typer.Exit`, an exception, Ctrl-C, SIGTERM and **SIGKILL** all release it — no manual step, and a killed process never blocks the run afterwards. **Re-entrant within a process:** a command that opens the same run twice (check whether any does) must not refuse itself.
- **L4. Per run, and reads are free.** Two different run ids spend at once. `status`, `cost`, `doctor`, `narration-stale` and every other command that does not open a run for models **never take it and work while a `narrate` holds it** — `narration-stale` above all, because it is what you run while one is going.
- **L5. No command can write `cost` unlocked, and a new one cannot forget.** Hypothesis: a test over the registered commands asserting each is on a named **read-only** list or a named **spending** list — a command on neither fails, which forces the decision (the shape of `tests/test_narration_selection.py`) — plus, for the spending ones, **a structural pin** in the pattern of `test_no_command_loads_a_checkpoint_outside_the_two_helpers`. Decide where `run` (a new run's id) and `write-drafts` (writes state, not `cost`) belong, and say why.
- **L6. A lost lock stops the run before the next spend.** A lock connection that dies mid-run (a network drop, a Postgres restart) silently turns the process back into an unguarded one. Before each ledger write (`RunLedger.record`, `_Narration.checkpoint`) check that the lock is still held — one cheap query — and if it is not, **stop, say so and record nothing further**: the clip already paid for is on disk and the next run reconciles. Use TCP keepalives on the lock connection. If you judge L6 unnecessary, say why in the report; do not just leave it out.
- **L7. Proven for real, not mocked.** Tests with **two real connections** and, for the kill, **a real child process killed with SIGKILL** (the `_durability_child.py` pattern): (i) a holder, then a refused second; (ii) release on normal exit, on an exception, and **after `kill -9`**; (iii) two run ids at once; (iv) the refused process wrote nothing and built nothing (exploding fakes); (v) same-process re-entry is not refused; (vi) a read-only command works while the lock is held; (vii) the order in L2; (viii) L6. Pytest must not leak a held lock between tests (a fixture releases it) and must still run **without the Vertex variables.**
- **L8. A zero-spend proof against the real ledger.** Hold the real run's lock from a second session (`psql` with `pg_advisory_lock` on the same key and a `pg_sleep`, or a long-lived zero-spend command), then run a spending command against `ikigai` — for example `narrate --run-id ikigai --render-only --no-synthesis --leaf 0` — and show: **refused, exit code 2, and the saved ledger identical before and after** (read it with `cost --run-id ikigai`; list `runs/ikigai/` file names and sizes before and after). Show `narration-stale` was never blocked. **Do not run a spending leg you cannot show costs nothing:** the refusal leg is free by construction; if "then it proceeds" could call a model, make it a test instead.

## Part 1 — the lock, item by item

**The hypothesis, checked against the code and the container, and where it disagrees.** A session-level advisory lock on a dedicated connection, keyed by the run id, in the one shared pipeline Postgres: **it holds.** Measured on `zoomout-pipeline-postgres` through Docker Desktop with a scratch probe before anything was built: the lock was free **2.2 ms** after a SIGKILL, **2.2 ms** after SIGTERM and **11 ms** after SIGINT; live, against the real ledger (below), **0.16 s** after `kill -9`, including the cost of asking. There is **no pooler**: `psycopg.connect` goes straight to `:5433` in `db/engine.py`, in `runner.py` (`PostgresSaver.from_conn_string`) and in `graph/build.py`; a transaction pooler would have defeated a session lock, so the README names that as the premise. Two refinements, neither a disagreement: advisory locks are **per database**, which is what makes the tests safe (the lock tests use the server's maintenance database `postgres`, where nothing can meet a lock on a real run), and `pg_locks` shows a bigint key as its high half in `classid` and its low half in `objid`, both unsigned, which is how the refusal finds the holder (`pg_locks` joined to `pg_stat_activity`).

**L1 — one spender per run, refused at once.** `hold_run(run_id, command=…)` is the first act of `run`, `resume`, `measure-breakdown`, `write-drafts`, `generate-assets`, `review-track`, `rewrite-leaf`, `balance-distractors`, `audition-voices` and `narrate`, **before `run_context()`** — so "before any client is built" is literally true, the Gemini client included — and `open_run_for_models` takes it again, which is not an error (L2's order). The refusal is red, bold, exit 2 like the paid-tier refusal, and says who: the lock's connection is named `zoomout-pipeline <command> <run> pid <pid>` (Postgres truncates `application_name` at 63 bytes, silently, so the pid stays whole and a long run id is shortened), read back with the holder's backend pid and how long it has held the run. No `--force`, no `--wait`: a queue behind a `narrate` is a second spender with a delay. **Evidence:** a real child holds the run and the parent is refused in under 2 s with the child's own name and pid (`test_a_second_process_is_refused_at_once…`); four real processes racing: exactly one wins (`…exactly_one_of_several_racing_processes…`); and for each of the ten commands, a real second session holds the run, **every client, graph and write is made to explode**, and the command is refused with exit 2 having reached none of them (`test_a_spending_command_is_refused_at_once…[<command>]`).

**L2 — taken before the checkpoint is read.** In `open_run_for_models`, `hold_run` comes before `read_run_state`; pinned **in the source** (AST: position within the function) and **behaviourally** (the order of lock, read and write, as it happens; and a helper called on a run held elsewhere is refused with its graph's `get_state` set to explode).

**L3 — held to the end, released on every end.** The locker keeps a registry of what this process holds, so the lock outlives the helper; taking it again is a no-op; a lock this process has *lost* stays lost (same reason, however many times it is asked); `atexit` closes cleanly; `release_all` closes only what its own pid took (a forked child must not send a goodbye on its parent's socket — K17). **Real children, really ended five ways** — normal exit, an exception, Ctrl-C (SIGINT), SIGTERM, **`kill -9`** — and after each the run is takeable again (`test_the_lock_is_released_however_the_holder_ends[…]`). *What a mutation can and cannot say here, honestly:* the release is the server's, not the code's, so the only breakages that make it fail are the ones that change **what holds the connection** — a transaction lock that lets go at once (K3), a connection that is dropped (K5), and a socket handed to a detached process that outlives the holder (K21, which turns the **SIGKILL and SIGTERM** legs red). The exit, exception and Ctrl-C legs are protected twice, as far as I can tell — by our `atexit` close and by the connection being closed cleanly when the interpreter tears it down (I did not trace which layer sends the goodbye) — so no single mutation of our code turns them red (K22, K23): they are experiments that confirm the premise, not guards on our code.

**L4 — per run, and reads are free.** Different run ids spend at once (`…two_runs_are_held_at_once…`), and the key is a hash of the run id that is **the same in every process** (`sha256`, not Python's per-process-salted `hash()` — a real child computes it and the parent compares; K2 is the `hash()` mutant and goes red). `status`, `cost`, `narration-stale` and `purge-raw-text` never name the lock and never ask it anything — asserted by a spy over the real locker — and each runs to its normal answer while a real session holds the run.

**L5 — no command writes `cost` unlocked, and a new one cannot forget.** Three groups, not two, because the code has three kinds of command: **spenders** (open a run for models, create one, or write its checkpoint: take the lock), **readers** (read a run, write nothing to it: never take it) and **no run id at all** (`doctor`, `init-db`, `attach-scenario-images`, `check-variety`, `contact-sheet`, `generate-covers`, `generate-greetings`). `test_every_command_is_sorted_into_exactly_one_group` fails on a registered command that is on none of the lists, with the message that says what to decide (C26 adds a `probe` command and goes red); a command takes a run id exactly when it is a spender or a reader (a command with no run id cannot open a run); each spender's `hold_run` is checked in the source for **once, as a statement of its own (not in a branch), under its registered name, before everything on a list of things that build or read** (`run_context`, `build_dependencies`, `read_run_state`, `open_run_for_models`, `open_run_for_narration`, `_Narration`, `require_paid_tier`, `get_settings`, `PayloadClient`, …); readers and no-run commands may not name `hold_run`, the helpers, `RunLedger`, `write_run_state` or `update_state`. **The structural pin in the pattern of `test_no_command_loads_a_checkpoint_outside_the_two_helpers`:** reading goes through two helpers; **writing goes through one, `write_run_state`, and no `update_state` call exists in `cli.py` anywhere else**, and that function asks the lock before it writes (an AST pin on each). **Where `run` and `write-drafts` belong:** both in the locked group. `run` writes the graph's checkpoints under whatever id it is given, `--run-id` can name a live run, and a generated id costs nothing to lock. `write-drafts` spends nothing and calls no model, but it reads the run, creates the **Track** in Payload when the run has none yet (`cms_node.py`: `if track_id is None: client.create_track(…)`) and writes the ids back, so two at once would each create a Track; it takes the lock and not the paid-tier check.

**L6 — a lost lock stops the writer before its next write.** Judged necessary and built. `require_held` asks **the lock's own connection what it holds** — a query on `pg_locks` for this connection's row, not just whether the connection answers (K8: a check that only asks "is it up" misses a connection that is alive and no longer holds the lock, and `test_a_connection_that_is_alive_but_no_longer_holds_the_lock_is_noticed` is what tells the two apart) — and a lost lock stays lost. TCP keepalives on both ends: libpq's (`keepalives_idle=15`, `interval=5`, `count=3`, `tcp_user_timeout=20000`, `connect_timeout=5`) so a dead server is noticed in seconds, and the server's own (`SET tcp_keepalives_*`) so it frees a vanished client's lock in about a minute rather than the operating system's two hours; and `idle_session_timeout` is set to 0 **for this connection only**, because it is idle by design between ledger writes and a server configured to drop idle sessions would take the lock with it (the test starts the connection with a 60 s idle timeout and asserts it was switched off; K20). Every `update_state` in `cli.py` goes through `write_run_state`, which asks first; on a lost lock it prints `THE RUN LOCK WAS LOST`, writes nothing and exits **1**. `RunLedger` knows how much it had not yet recorded (entries since its last write that reached the checkpoint) and the message says it (`Not recorded: $0.0100.`); a clip already paid for is on disk and the next run reuses it. **Exclusion, said plainly:** the spend in flight when the lock goes is the only one that can follow the loss (the check is at the next ledger write, right after each paid call), and `run`/`resume`'s in-graph writes are not checked at all — ruling 2.

**L7 — proven for real, not mocked.** (i) a holder, then a refused second: `test_a_second_process_is_refused_at_once_and_told_who_holds_the_run`, `test_a_session_that_is_not_a_command_is_named_too` (a `psql` window). (ii) release on normal exit, on an exception, after `kill -9` (and SIGTERM and SIGINT), with a **real child**: `test_the_lock_is_released_however_the_holder_ends[exit|raise|SIGKILL|SIGTERM|SIGINT]`. (iii) two run ids at once: `test_two_runs_are_held_at_once_and_neither_blocks_the_other`. (iv) the refused process wrote nothing and built nothing, **with exploding fakes**: the ten parametrised refusals. (v) same-process re-entry is not refused: `test_taking_the_lock_again_in_the_same_process_is_not_refused` (and it is one connection, not two). (vi) a read-only command works while the lock is held: `test_status_and_cost_work_…`, `test_narration_stale_works_while_a_narrate_holds_the_run` (the whole stale check against Leaf 9's real shape), `test_purge_raw_text_works_…`. (vii) the order in L2: above. (viii) L6: `test_a_lock_connection_that_dies_is_noticed_and_stays_lost` (the server terminates the backend), `…alive_but_no_longer_holds_the_lock…` (`pg_advisory_unlock_all` on its own connection), `test_a_lock_that_really_died_stops_the_ledger_before_it_writes` (real lock, real termination, real door), and the unrecorded-figure tests. **No lock leaks between tests**: the `hold_elsewhere` fixture closes every foreign session and then fails the test if any advisory lock is still held in the database; **and the suite never takes a lock in the real database** — an autouse fixture (`hermetic_run_locks`, in `conftest.py`) puts a locker that holds nothing and refuses nothing in front of every test, because most of the suite drives `narrate` under the run id `ikigai` with a faked graph, and a `pytest` run on this machine would otherwise have taken (or been refused) a lock on the real `ikigai`. The lock's own tests opt out (`real_run_locker`) and use the maintenance database. **pytest runs without the Vertex variables** and needs only the database URL; it skips loudly if Postgres is down, like the other database tests.

**L8 — the live proof, against the real `ikigai` ledger, $0.** Before: `cost --run-id ikigai` read **$6.5755 / 1,606,989 tokens**; the checkpoint table (the pipeline's own database) held **829 rows** for the thread, latest checkpoint `1f1be92e-ef78-639c-833b-795f4ea2d8d6`; `runs/` snapshotted. ## What I got wrong, and what surprised me

- **I overwrote five of my own mutation results and caught it before reporting.** Part 2's mutation ids `C1` and `K1`–`K4` collided with Part 1's, the harness keys its results by id, and so Part 1's rows for "`run` does not take its lock" and the four key/lock mutants were silently replaced by Part 2's. I found it while building these tables (a count that did not add up), renamed Part 2's, and re-ran the five Part 1 mutants: all red, with the same counts as the first time. Every number in the tables above is from the re-run results on disk.
- **My first test of the per-clip logging called `monkeypatch.undo()` in the middle of a test**, to put a patch back — which also undid the autouse fixture that keeps every test off the real run locks. The test failed confusingly (the command logged no hold at all), and I believe it is because the environment's database URL names `zoomout_pipeline_test`, which does not exist, so the real locker could not connect and the command stopped (I did not capture its output to confirm). Had that URL named the real database, the un-hermetic locker would have taken a lock on the real `ikigai`. Rewritten as three tests with no `undo()`. **A safety fixture and `monkeypatch.undo()` do not mix.**
- **K11 survived** (above): a release that did nothing, hidden by garbage collection. A test of "released" has to keep the thing it expects to be released alive.
- **The child process printed debug logs before it said `HELD`**: structlog unconfigured prints every event to stdout, and the parent reads that stream line by line. The child now configures logging as the CLI does, silent below an error. The same unconfigured logging put a debug line where my live-proof holder was meant to print its pid (cosmetic: the holder's name carries its pid).
- **The unknown-leaf message and the new rule each broke an existing assertion in a way I should have predicted:** the fabricated reviews only counted clips. Named above.
- **The fork test adds a `DeprecationWarning`** (the process is multi-threaded by then): it made the warning count 62 against the baseline's 61 until I traced it and filtered that one warning on that one test.
- **A cosmetic wart I left:** in the refusal text for a holder that is a pipeline command, the "stop it" line wraps at "The" (`… on the machine that started it). The` / `server frees the run …`). It is in the live output above. It does not change a word of meaning and a fix would reopen a package that is otherwise closed.
- **In the good direction:** the hypothesis held on the first measurement; and the live proof found nothing — no refusal that did not refuse, no reader that blocked, no lock left behind.

## What I could not verify

- **A lost lock mid-`run` or mid-`resume`** (ruling 2): not detected by design, and not exercisable for $0.
- **That the keepalives do what they claim under a real network black hole.** I verified they are *set* on both ends (client parameters read back from the connection, server settings read with `SHOW`); I did not drop a network.
- **A role that is not a superuser.** The pipeline connects as `postgres`, which can read other sessions' `application_name` in `pg_stat_activity`; a restricted role would see them blank and the refusal would say "holder: not found" (it still refuses, and says to run again). No test uses such a role.
