## Part 2 — T1–T6, item by item

**T1 — whose lock is it.** On real connections: the lock's own session runs `pg_advisory_unlock_all()`, then a foreign session takes the same key, and `require_held` must raise `RunLockLostError` ("no longer lists this lock"). Without `AND pid = pg_backend_pid()` the query finds the foreign session's row and answers "held". Red: T1a.

**T2 — the key, by literal.** `lock_key("ikigai") == 4323921442082563206` and `lock_key("a") == -1813165551407439184`. **How they were derived, without `lock_key`:** in Postgres itself — its own `sha256` over `zoomout-pipeline/run-lock/v1:<id>`, the first eight bytes as a signed bigint, `select ('x' || substr(encode(sha256('…'::bytea), 'hex'), 1, 16))::bit(64)::bigint` — and again with `openssl dgst -sha256 -binary | xxd -p -l 8` and **bash**'s signed 64-bit arithmetic (zsh's `$((16#…))` truncates it; I got a wrong value there first). The two agree, and `test_the_literals_are_what_postgres_itself_computes` re-runs the Postgres derivation on every run, so a wrong literal would fail as itself and not only the function. `a` is the negative one, the branch a uuid-random test id reaches by luck. One test holds `a` from a second session and requires the refusal to find the holder by name; another takes `a` and requires `require_held` to find it. **Red, deterministically:** the namespace mutant (T2a: the literal pin), `abs(key)` in `_lock_row_ids` (T2b: the two negative-key tests), and a third I added, the key read as unsigned (T2c: `a` overflows a bigint). *Deterministic is measured*: the new T2 tests alone, run three times each against each mutant, were red 1, 2 and 3 tests every time. The totals in the full-file runs are **not** stable — T2b read 8 then 5 and T2c 7 then 13 across two campaigns — because the older lock tests take `new_run_id()`, a random id whose key is negative half the time.

**T3 — the graph's other writers.** `GRAPH_DOOR = {invoke, stream, ainvoke, astream}` joins `LOCK_AND_WRITE_NAMES`, so a command filed as a reader or as a no-run command may not name any of them. A new pin, `test_the_only_commands_that_write_through_the_graph_are_run_and_resume`, finds every command whose body names one and requires exactly `{run, resume}`, both of them on the spenders' list, **and says why in its docstring**: they write through the checkpointer, which `write_run_state`'s lock check never sees; they take the lock first and hold it; they would not notice losing it (LEDGER-1 ruling 2, still open). **T4 — the hermetic fixture cannot be undone into the real locker.** *Shape, and where it departs from the handoff's hypothesis:* the handoff suggested a session-scoped fixture that assigns the module attribute instead of the function-scoped `monkeypatch`. **T5 — a foreign database is a refusal, not a traceback.** `hold_run` catches `ForeignDatabaseError` and prints `REFUSING TO USE THIS DATABASE` and the error's own message (what it found; `ZOOMOUT_PIPELINE_DATABASE_URL`, what to change) in red, exit **1**. **Why 1 and not 2:** this is the environment being wrong — `doctor` exits 1 for the same condition, in the same words, and so does a lock that could not be taken (`RunLockUnavailableError`) in the same function; 2 is what the code uses for a refusal about the run or the arguments (held, in use, the paid tier, an unknown Leaf). ## What I got wrong, and what surprised me

- **My characterization asserted the wrong thing about the Track link, and copied the same claim into the guard's docstring.** The first version of `test_without_the_guard_…` built its fresh state by hand, without `cms_track_id`, and asserted the Track link *survives* — what the handoff's experiment saw and what I took on trust. The command builds its state differently. Nothing failed: it was green. I found it by reading the dropped-guard mutant's full failure output (`cms_track_id: None != 50`) for a different reason, and corrected it in `bc4d50f`. **Evidence for "what the command did" has to run the command**: a hand-built stand-in for its input can share a blind spot with the experiment it was built from.
- **The damage line printed the last eight characters of a checkpoint id**, which are the same for every checkpoint one process writes, so on a real failure it would have read `1f1bfcda -> 1f1bfcda` and looked as if nothing had been written, directly above a "Differing attributes" list that names `checkpoint_id`. Whole ids now. Found by reading the saved output of the "show" run, not by a test.
- **My first one-digit mutant was not the handoff's** (T6a vs T6a2, above). It was red, which is exactly how it hid that the discriminating test was green under it: "unreadable is never overwritten" covers for it. Running both is what showed which test earns its place.

- **A constant shadowed.** My T6 block re-bound the module's `BOOK` (the `Session` stub uses it) to another string, and six unrelated review tests failed in the full run while the file alone was green. Renamed `REVIEW_NAME`. A test module's constants are shared with everything below them.

- **The mutation counts for T2b and T2c moved between campaigns** (8 → 5, 7 → 13) for the reason given under the table; I should have expected it from the handoff's own remark that `new_run_id()` reaches the negative branch "by luck".

Tightened in `aa9c181`; the message of `bc4d50f` carries the stronger wording and is history. The same fault as the first bullet, one level up: a claim about what someone else ran, stated as seen.
